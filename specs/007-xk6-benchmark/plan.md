# Implementation Plan: xk6 Benchmark Suite for Producer App

**Branch**: `007-xk6-benchmark` | **Date**: 2026-02-20 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/007-xk6-benchmark/spec.md`

## Summary

A k6-based benchmark suite using the xk6-faker extension to load-test the producer app REST API. The suite covers three scenarios (sustained 500 RPS, ramp-up, and stress test), generates realistic fake data for Users and Videos (and Comments when the endpoint ships), maintains referential integrity via a pre-seeded ID pool, and produces machine-readable JSON reports with PASS/FAIL threshold verdicts.

---

## Technical Context

**Language/Version**: JavaScript (k6 scripting runtime — Goja JS engine, ES6 subset)
**Primary Dependencies**: xk6 v1.x (custom k6 binary builder), xk6-faker (Grafana official faker extension), grafana/k6 Docker image, grafana/xk6 Docker builder image
**Storage**: N/A (benchmark is a client; no persistent storage of its own)
**Testing**: k6 built-in thresholds and summary; `handleSummary` for JSON export
**Target Platform**: Linux container (Docker), multi-arch (amd64 + arm64)
**Project Type**: Single service (benchmark runner as Docker container)
**Performance Goals**: Generate ≥ 500 RPS sustained; stress scenario must reach 1000+ RPS to find saturation point
**Constraints**: Benchmark runner itself must NOT be the bottleneck (NFR-001: capable of ≥ 1000 RPS from single host); p95 threshold 50ms measured at producer, not network edge
**Scale/Scope**: 3 scenarios × 3 entity types; pre-seeded pool of 200 users + 100 videos

## Implementation Phases

### Phase 1 — Core Infrastructure

1. **Dockerfile** (multi-stage xk6 build)
   - Stage 1: `FROM grafana/xk6` — `xk6 build --with github.com/grafana/xk6-faker`
   - Stage 2: `FROM grafana/k6:latest` — copy compiled binary
   - Output: `data-sync/benchmark:latest` image

2. **Root `docker-compose.yml`** — add `benchmark` service entry
   - Profile: `benchmark` (opt-in; not started with default `docker compose up`)
   - Network: inherits default compose network (same as `producer`)
   - Entrypoint: `k6 run /scripts/main.js`
   - Volumes: mounts `./benchmark/scripts` and `./benchmark/reports`
   - Env vars sourced from root `.env` / environment

3. **Root `.env.example`** — append benchmark vars alongside existing service vars
   - `BENCHMARK_BASE_URL`, `BENCHMARK_SCENARIO`, `BENCHMARK_TARGET_RPS`, etc.
   - Uses `BENCHMARK_` prefix to avoid collisions with existing service vars

4. **`benchmark/Makefile`** — targets: `build`, `run-sustained`, `run-ramp`, `run-stress`, `clean`
   - Delegates to `docker compose --profile benchmark run benchmark ...` from repo root

### Phase 2 — Shared Library (`scripts/lib/`)

5. **faker.js** — data builders
   - `buildUser()` → `{ username, email }`
   - `buildVideo(userId)` → `{ user_id, title, description, duration }`
   - `buildComment(videoId, userId)` → `{ video_id, user_id, comment_text }` (placeholder for future endpoint)

6. **client.js** — HTTP helpers
   - `createUser(baseUrl)` → `{ response, userId }`
   - `updateUser(baseUrl, userId)` → response
   - `deleteUser(baseUrl, userId)` → response
   - `createVideo(baseUrl, userId)` → `{ response, videoId }`
   - All calls include endpoint tag and `Content-Type: application/json` header

7. **thresholds.js** — shared export:
   ```javascript
   export const thresholds = {
     http_req_duration: ['p(95)<50'],
     http_req_failed:   ['rate<0.01'],
   };
   ```

### Phase 3 — Scenario Scripts (`scripts/scenarios/`)

8. **sustained-load.js**
   - Executor: `constant-arrival-rate`, 500 RPS, 120s
   - `setup()`: seed 200 users + 100 videos via producer API
   - Default function: random weighted CRUD mix (40% create user, 20% update user, 10% delete user, 30% create video)
   - `handleSummary()`: write `sustained-summary.json` + stdout table

9. **ramp-up.js**
   - Executor: `ramping-arrival-rate`
   - Stages: 30s→50 RPS, 30s→200 RPS, 30s→500 RPS, 60s hold, 15s ramp-down
   - Same CRUD mix; same `handleSummary` pattern

10. **stress.js**
    - Executor: `ramping-vus`
    - Stages: 30s→50 VU, 60s→200 VU, 60s→400 VU, 20s→0
    - Thresholds NOT abort-on-fail (collect full data through saturation)
    - `handleSummary()` annotates the inflection point (RPS where error rate first exceeds 5%)

### Phase 4 — Entry Point and Routing

11. **main.js** — reads `__ENV.SCENARIO`, imports and runs the matching scenario module
    - Pre-flight health check before delegating to scenario
    - Fallback: error on unknown `SCENARIO` value

## Key Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Executor for 500 RPS scenario | `constant-arrival-rate` (open model) | Avoids coordinated omission; accurately simulates real traffic independent of response time |
| Executor for stress scenario | `ramping-vus` (closed model) | VU count is the independent variable when finding saturation; concurrency ceiling is what matters, not iteration rate |
| Fake data uniqueness | UUID prefix for email, timestamp suffix for username | Prevents 409 Conflict without requiring cleanup between runs |
| Referential integrity | `setup()` seeds ID pools; VUs draw from SharedArray | Thread-safe; IDs are guaranteed to exist when VUs start |
| Report format | JSON summary + NDJSON raw | Summary is CI-friendly (small, structured); raw NDJSON is time-series-friendly for Grafana dashboards |
| Comments scenario | Placeholder builders only (no active requests) | Comments endpoint not yet implemented in producer; scripts are structured to add the scenario as a one-file addition |

## Dependencies and Assumptions

- Producer app (006-producer-app) must be running and healthy before benchmark starts
- Docker network connectivity between `benchmark` and `producer` containers
- `POST /api/v1/users` and `POST /api/v1/videos` are the only write endpoints with full CRUD; benchmark focuses on these until Comments endpoints are shipped
- Database state accumulates during testing (no cleanup required per spec A-005)
- Reports directory is git-ignored; CI must archive as an artifact explicitly

## Open Items / Risks

| Item | Risk | Mitigation |
|---|---|---|
| Comments endpoint not yet implemented | Benchmark cannot exercise full entity mix | Placeholder builders ready; add scenario in same PR as Comments endpoint |
| Video UPDATE/DELETE not yet routed | Limits CRUD coverage for videos | Plan includes video update/delete in CRUD mix once routed |
| Pool exhaustion during DELETE-heavy runs | DELETE reduces pool; subsequent DELETEs get 404 | 404 on DELETE is treated as expected (not a failure); pool rotation handles gracefully |
| xk6-faker API changes between versions | Method signatures may change | Pin `xk6-faker` to a specific release tag in Dockerfile `xk6 build --with ...@vX.Y.Z` |
